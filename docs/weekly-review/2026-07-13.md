### Positive Observations

- **`WorkEntryDao` is correctly annotated.** Every multi-step DB operation (`replaceEntryWithTravelLegs`, `upsertAllAndDeleteTravelLegs`, `readModifyWrite`) carries `@Transaction`, and the comment in `readModifyWrite` honestly explains the limits of DB-level atomicity vs. repository-level serialisation. This is exemplary.
- **Per-date locking in `RoomWorkEntryRepository` is well-engineered.** The `LinkedHashMap<LocalDate, DateMutex>` with reference counting and LRU-style trimming elegantly prevents concurrent writes to the same day without global locks.
- **`WindowCheckWorker` correctly handles `CancellationException`** (re-throws it before the broad `catch (e: Exception)` block) and uses a per-instance mutex to make check-show-flag atomic within one execution. The `shouldRetryOn()` helper limiting retries to `IOException` and `SQLiteException` is a good pattern.
- **`LazyColumn` items all carry stable `key` lambdas** (`key = { entry -> entry.date }` in `HistoryScreen`). This is correct practice and prevents unnecessary recomposition when the list order changes.
- **`CsvCellEncoder` defends against CSV injection** (formula-prefix quoting) and correctly handles embedded semicolons, quotes, and newlines. The UTF-8 BOM write is also intentional and appropriate for German-locale Excel compatibility.

### Top 3 Recommendations

1. **Fix `CsvExporter.exportToCsv()` to run on `Dispatchers.IO`.** This is the highest-severity standing bug: file I/O on the main thread will cause measurable jank or ANR on any device exporting more than a few hundred entries. The fix is a one-line change to match `PdfExporter`'s existing pattern — no architecture change needed.

2. **Standardise `CancellationException` handling across all coroutine catch blocks.** `OverviewViewModel` and `EditEntryViewModel` already do this right; `SettingsViewModel`, `TodayActionsHandler`, and the export path do not. A global search for `catch (e: Exception)` inside `viewModelScope.launch` and `withContext` blocks (and checking each for a preceding `catch (e: CancellationException)`) would clean this up in one PR.

3. **Address the `!!` operator in `EditEntryTravelSections.kt:256`.** A null `paidMinutesOverride` on a new travel leg is reachable in normal usage; the crash would appear as a compose exception with no user-visible error message. A safe-call with an appropriate fallback string is a two-line fix that prevents a silent NullPointerException in the edit flow.
